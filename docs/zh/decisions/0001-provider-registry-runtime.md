3|# 0001：提供者、注册中心、运行时
4|
5|## 状态
6|
7|已采纳。
8|
9|## 背景
10|
11|原始的工具系统混合了静态工具定义、handler 查找和运行时调用。对于少量内置工具来说这是可行的，但它没有为 MCP 留下干净的路径——在 MCP 中，工具是动态发现的，且提供者可以独立失败。
12|
13|我们需要一个模型，既能支持内置工具，又能支持外部提供者，而不需要让 agent 循环了解每种来源类型。
14|
15|## 决策
16|
17|使用三个层次：
18|
19|- 提供者：从一个来源加载工具并返回 `RegisteredTool[]` 及诊断信息。
20|- 注册中心：存储已注册的工具和提供者诊断信息。
21|- 运行时：通过注册中心调用工具。
22|
23|agent 循环只接收工具定义并调用运行时调用。
24|
25|## 后果
26|
27|好的方面：
28|
29|- 工具来源的差异保持在循环之外。
30|- MCP 可以作为另一个提供者添加。
31|- 注册中心可以在不注册损坏工具的情况下解释不可用的命名空间。
32|- 运行时不再需要自己的 handler 映射。
33|
34|权衡：
35|
36|- 启动组装更加显式。
37|- 测试需要在更多地方构建 registry/runtime。
38|
39|## 不变量
40|
41|- `RegisteredTool.name` 必须等于 `definition.name`。
42|- 重复的工具名称会导致注册失败。
43|- 提供者诊断信息不得包含秘密。
44|- 循环不得导入提供者。
